# 트래버스: 큰 토크에서 핸들을 감았다 풀었다 하는 증상 분석과 수정 (2026-11-11)

Claude(AI)가 Codex(AI)와 교차검토하며 작성했다. 교차검토는 분석·코드 검토이고, 실차 사용 승인이 아니다.
아래에서 **관측**은 콤마에 남은 주행 로그에서 직접 읽은 값, **계산**은 그 로그를 재생하거나 소스 함수를 옮겨 계산한 값, **추정**은 아직 확정하지 못한 해석이다.

## 증상

- 같은 차·같은 콤마에서 FrogPilot은 조향 토크가 커져도 핸들 각도가 안정적이었다.
- carrotpilot은 커브가 클수록(토크가 클수록) 핸들을 세게 감았다 풀었다를 반복하다 차선을 벗어났다.

## 쓴 자료

- 콤마의 10/27~11/11 carrotpilot 주행 31개 qlog(10 Hz) 전수, 문제 구간 rlog(100 Hz).
- 비교 기준 FrogPilot: 사용자 포크 `testing-v1-apn`(FrogPilot 2026-02 계열) 소스. 당시 FrogPilot 주행 로그와 설정은 남아 있지 않다(기본값이면 NNFF 켜짐).
- 사용자가 만든 `latcontrol_torque.py` 수정본(측정값 미분 D항 추가).

## 원인

1. **토크 변화율이 느림(관측).** 수정 전 커밋 `d0ca2cbd`는 40 ms마다 +6/−8(최대 400)로 보냈다(일부 문제 주행은 기기에 미커밋 `STEER_STEP 3`이 있던 때라 30 ms마다 +6). 0→300에 2.0초가 걸린다(FrogPilot은 30 ms마다 +10/−15, 0.9초). 시속 54 km 이상 조향 시간의 10~53%, 토크 200 이상 구간의 43~100%에서 요청과 출력이 벌어졌다. 최악 사례는 요청이 ±1.0에 붙은 채 출력이 뒤따르고, 6~17초 사이 오차 방향이 5~8번 뒤집힌 뒤 운전자가 개입했다.
2. **EPS 보고 토크가 300 근처에서 더 오르지 않음(관측).** `CustomSteerMax=400`이었지만 `LKATorqueDelivered` 보고값은 명령 약 300 이상에서 약 3.00에 머물렀다. 이 범위의 명령은 토크를 줄일 때 300까지 내려오는 시간만큼 지연을 만든다(추정, EPS의 물리 한계는 확인하지 못함).
3. **측정 횡가속도 과대(관측).** `CustomSR`(12.8~14.0)이 학습 조향비(18.7~19.3)를 덮어써, 조향각으로 계산한 횡가속도가 요레이트 기준의 1.35~1.47배였다(상관 0.96~0.996). 학습 조향비도 같은 요레이트로 학습하므로 완전히 독립된 두 센서 비교는 아니다.
4. **선형 피드포워드 과잉(관측+계산).** 이 차는 횡가속 1.73 m/s²에 토크 약 0.74, 3.1 m/s²에서 1.0(포화)이었다. 수정 전 선형 FF는 같은 점에서 1.12/2.01로 두 예에서 약 1.5~2.0배를 요구했다. 큰 커브에서 I항이 FF와 반대로 크게 쌓였고(+0.79, +1.38), 목표가 크게 풀리는 순간 요청이 +400→−400으로 뒤집혔다(이 순간에는 운전자 개입도 함께 있었다). 트레일블레이저 NNFF 모델의 정상상태 계산값은 0.62/0.83이다.

토크가 클수록 나빠지는 이유(추정): 2는 300 이상에서만, 1은 토크 변화량에 비례해 지연이 길어지고, 3·4의 오차는 횡가속도에 비례해 커진다.

## 사용자 수정 파일 평가

- FrogPilot은 일반 토크 경로와 NNFF 경로 모두 D 이득이 0이다. "FrogPilot에 D항이 있어서 안정적"이라는 전제는 맞지 않다.
- 수정본을 현재 설정(`LateralTorqueKd=1000` → 10.0)으로 쓰면 D항이 단위 변환 없이 횡저크에 곱해진다. 10 Hz 로그로 재구성하면 D항 중앙값 0.47, 시간의 28%는 D항 혼자 출력 한계 1.0을 넘었다(P항 중앙값 0.04, 계산). 재인게이지 첫 미분도 크게 튄다. 그대로 쓰지 않는 것이 맞다.
- FrogPilot NNFF는 조향 속도로 만든 저크를 NN 입력에 넣는다. 이번 수정은 이 입력 경로를 트래버스에 맞췄다. 그것이 실제로 감쇠를 만드는지는 실차로 확인해야 한다.

## 수정 내용 (브랜치 `fix_pls`)

코드
- `opendbc/car/gm/values.py`: 트래버스만 `STEER_STEP 3`, `STEER_DELTA_UP 10`, `STEER_DELTA_DOWN 15`.
- `opendbc/car/gm/carcontroller.py`: `CustomSteerMax`를 300 이하로 제한(GM 전체).
- `selfdrive/controls/lib/latcontrol_torque.py`: 트래버스 + NNFF일 때 FrogPilot NNFF와 같게 저속표·저크 입력, 저크 시간은 `CP.steerActuatorDelay + 0.2`(0.4 s). 조향 속도로 계산한 저크가 유한하지 않으면 0. 다른 차종의 NNFF, NNFF-lite, 선형 경로는 그대로.
- 테스트: `test_traverse_steering_timing.py`, `test_latcontrol_low_speed.py`, `test_latcontrol_traverse_nnff.py`.

설정(콤마)
`CustomSR 0`, `CustomSteerMax 300`, `CustomSteerDeltaUp 10`, `CustomSteerDeltaDown 15`, `NNFF 1`, `LateralTorqueCustom 1`, `LateralTorqueKpV 100`, `LateralTorqueKiV 30`, `LateralTorqueKf 100`, `LateralTorqueKd 0`, `LateralTorqueAccelFactor 2500`, `LateralTorqueFriction 0`. `SteerActuatorDelay 30`, `LatSmoothSec 20`은 그대로.
`LateralTorqueAccelFactor`는 선형 경로와 NN 모델 입력이 없을 때의 폴백에서 쓰이고, NN 피드포워드 배율이 아니다.

## 알려 둘 기존 위험 (이번 범위 밖)

- carrot/kan-sky 판다 `safety_gm.h`는 조향 토크 검사가 실패해도 송신을 막는 줄(`tx = false`)이 주석 처리돼 있다. 판다가 잘못된 조향 명령을 막아 준다고 가정할 수 없다.
- 판다는 감소 한계를 25로 선언하지만, 운전자가 반대로 힘을 줄 때 호스트는 15씩(수정 전 8~13씩) 줄인다. 이 경우 검사 위반이 생기고, 위반 뒤 검사기가 0으로 초기화돼 큰 커브 동안 연쇄 위반이 이어질 수 있다(기전은 계산으로 확인, 각 주행의 첫 위반 원인은 미확정).
- 판다 안전 코드 변경은 이전에 사용자가 중단한 범위라 이번에 건드리지 않았다.

## 검증하지 못한 것

- 실제 주행에서 증상이 사라졌는지. 재생은 개방 루프라 확정할 수 없다. Codex는 이 상태를 "일상 사용 승인 전"으로 판정했다.
- 시동을 건 상태의 card·controlsd 실제 객체(오프로드에서는 뜨지 않는다).
- 실제 0x184 수신·0x180 송신 순서로 재현한 판다 검사, 판다 펌웨어 바이너리 동작, EPS 물리 토크 한계.
- 새 저크 입력의 실제 잡음 영향, NN 모델 폴백·재인게이지 전이.

## 첫 주행 때

- 교통과 떨어진 안전한 곳에서, 직선과 완만한 커브부터 확인한다. 예전에 차선을 벗어났던 급커브를 첫 확인 장소로 쓰지 않는다.
- 양손을 핸들에 두고 언제든 바로 조향을 되찾을 준비를 한다. 운전 중 설정을 바꾸지 않는다.
- 의도하지 않은 감았다 풀기, 반대 조향, 차선 가장자리로 밀림, EPS·CAN 경고가 한 번이라도 나오면 즉시 개입하고 해제한 뒤 안전하게 멈춘다. 그 시각을 기록해 두면 로그로 확인할 수 있다.
