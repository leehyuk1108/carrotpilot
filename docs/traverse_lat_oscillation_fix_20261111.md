# 트래버스: 큰 토크에서 핸들을 감았다 풀었다 하는 증상 분석과 수정 (2026-11-11)

Claude(AI)가 Codex(AI)와 교차검증하며 작성했다. 수치는 콤마에 남아 있던 실제 주행 로그에서 나왔다.

## 증상

- 같은 차·같은 콤마에서 FrogPilot은 조향 토크가 커져도 핸들 각도가 안정적이었다.
- carrotpilot은 커브가 클수록(토크가 클수록) 핸들을 세게 감았다 풀었다를 반복하다 차선을 벗어났다.

## 쓴 자료

- 콤마의 10/27~11/11 carrotpilot 주행 31개 qlog(10 Hz) 전수, 대표 4구간 rlog(100 Hz).
- 비교 기준 FrogPilot: 사용자 포크 `testing-v1-apn`(FrogPilot 2026-02 계열) 소스.
- 사용자가 만든 `latcontrol_torque.py` 수정본(측정값 미분 D항 추가).

## 원인 (로그로 확인)

1. **토크 변화율 제한이 너무 느림.** 현재 코드는 40 ms마다 +6/−8(최대 400). 0→300에 2.0초가 걸린다(FrogPilot은 30 ms마다 +10/−15, 0.9초). 시속 54 km 이상 조향 시간의 10~53%, 토크 200 이상 구간의 43~100%가 제한에 묶였다. 최악 사례는 제어기가 최대 토크(±1.0)를 요구한 채 출력이 뒤따라가고, 6~17초 사이 오차 방향이 5~8번 뒤집힌 뒤 운전자가 개입했다.
2. **EPS가 내지 못하는 토크를 요구함.** `CustomSteerMax=400`이었지만 EPS가 보고한 토크(`LKATorqueDelivered`)는 명령 약 300 이상에서 약 3.00에 머물렀다. 300~400 구간은 효과 없이 토크를 줄일 때 지연만 만든다. 판다의 조향 토크 검사 실패 시 차단 줄이 주석 처리돼 있어 400이 그대로 나갔다.
3. **측정 횡가속도 과대.** `CustomSR`(12.8~14.0)이 학습된 조향비(18.7~19.3)를 덮어써서, 조향각으로 계산한 횡가속도가 요레이트로 잰 값의 1.35~1.47배였다(상관 0.96~0.996). 제어기는 차가 실제보다 더 돈다고 판단했다.
4. **선형 피드포워드 과잉.** 이 차는 횡가속 1.73 m/s²에 토크 약 0.74, 3.1 m/s²에 1.0(포화)이 들었다. 기존 선형 FF는 같은 점에서 1.12/2.01을 요구했다(1.5~2.4배). 큰 커브에서 FF가 넘치면 I항이 반대로 쌓이고(+0.79, +1.38), 커브가 풀리는 순간 요구 토크가 +400→−400으로 뒤집혔다. 트레일블레이저 NNFF 모델은 같은 점에서 0.62/0.83으로 실제와 가깝다.

토크가 클수록 나빠지는 이유: 2는 300 이상에서만, 1은 토크 변화량에 비례해 지연이 길어지고, 3·4의 오차는 횡가속도에 비례해 커진다.

## FrogPilot과 다른 점

| 항목 | carrot(수정 전) | FrogPilot | 수정 후 |
|---|---|---|---|
| LKA 명령 주기·변화량 | 40 ms, +6/−8 | 30 ms, +10/−15 | 30 ms, +10/−15 (트래버스만) |
| 최대 명령 | 400 | 300 | 300 (GM 전체 상한) |
| 조향비 | CustomSR 고정 | 학습값 | 학습값 (`CustomSR=0`) |
| 피드포워드 | 선형, Kf 1.7 / 계수 3.5 | NNFF(트레일블레이저) | NNFF(같은 모델 파일) |
| PID | Kp 2.0, Ki 0.8, Kf 1.7 | 1.0 / 0.3 / 1.0 | 1.0 / 0.3 / 1.0 |
| NN 저속 보정표 | 해당 없음 | [12,3,1,0] | [12,3,1,0] (트래버스) |
| 조향각 차량의 저크 입력 | 항상 0 | 사용 | 사용 (트래버스) |
| 저크 시간 | 0.6 s | 지연(약 0.38~0.40 s) | 0.4 s (트래버스) |
| NNFF 마찰 보정 | 해당 없음 | 사실상 0 | 0 (`LateralTorqueFriction=0`) |

남은 차이(이번에 안 바꿈): PID 적분 제한 방식, pitch 입력, 목표 곡률 평활화(`LatSmoothSec`, `SteerActuatorDelay`), 차량 제원 기본값, 재인게이지 시 I 초기화.

## 사용자 수정 파일 평가

- FrogPilot은 일반 토크 경로와 NNFF 경로 모두 D 이득이 0이다. "FrogPilot에 D항이 있어서 안정적"이라는 전제는 맞지 않다.
- 수정본을 현재 설정(`LateralTorqueKd=1000` → 10.0)으로 쓰면 D항이 단위 변환 없이 횡저크에 곱해진다. 로그로 재구성하면 D항 중앙값 0.47, 시간의 28%는 D항 혼자 출력 한계 1.0을 넘었다(P항 중앙값 0.04). 재인게이지 첫 미분도 크게 튄다. 그대로 쓰지 않는 것이 맞다.
- 다만 방향은 일리가 있다. FrogPilot NNFF는 조향 속도에서 만든 저크를 NN 입력으로 넣어 제한된 크기의 감쇠를 얻는다. 이번 수정은 이 방식을 트래버스에 맞췄다.

## 수정 내용 (브랜치 `fix_pls`)

코드
- `opendbc/car/gm/values.py`: 트래버스만 `STEER_STEP 3`, `STEER_DELTA_UP 10`, `STEER_DELTA_DOWN 15`.
- `opendbc/car/gm/carcontroller.py`: `CustomSteerMax`를 300 이하로 제한.
- `selfdrive/controls/lib/latcontrol_torque.py`: 트래버스 + NNFF일 때 FrogPilot NNFF와 같게 저속표·저크 입력·저크 시간. 비유한 조향 속도는 0으로.
- 테스트: `test_traverse_steering_timing.py`, `test_latcontrol_low_speed.py`, `test_latcontrol_traverse_nnff.py`.

설정(콤마)
`CustomSR 0`, `CustomSteerMax 300`, `CustomSteerDeltaUp 10`, `CustomSteerDeltaDown 15`, `NNFF 1`, `LateralTorqueCustom 1`, `LateralTorqueKpV 100`, `LateralTorqueKiV 30`, `LateralTorqueKf 100`, `LateralTorqueKd 0`, `LateralTorqueAccelFactor 2500`(NNFF가 꺼질 때만 쓰임), `LateralTorqueFriction 0`. `SteerActuatorDelay 30`, `LatSmoothSec 20`은 그대로.

## 검증한 것

- 기기 pytest: 수정 전 886 통과/11 실패 → 수정 후 938 통과/11 실패. 실패 11개(GM CC 차종 지문 8, 다른 제조사 포화 테스트 3)는 수정 전과 같은 기존 실패.
- 기기 실제 코드·설정으로 실행: NNFF 사용(트레일블레이저 모델, sha256 `2a8dfbfb…`), 컨트롤러 3/10/15/300, 1.2초에 LKA 명령 39개(수정 전 29개), 0.9초 시점 토크 290(수정 전 132).
- 문제 주행 6구간을 새 제어기에 재생(기존 차량 궤적 고정, 개방 루프, 출력 제한 시 I항 동결 되먹임, 앞 구간 예열, 같은 CAN 기준):

| 구간 | 측정/요레이트 | 큰 커브 FF(CAN) | 100 CAN 넘는 요청 반전 | I가 FF와 반대(90 CAN 초과) | EPS 한계 요청 |
|---|---|---|---|---|---|
| 000001ec seg121 | 1.35 → 1.02 | 656 → 213 | 6 → 0 | 65% → 35% | 17.6% → 9.7% |
| 000001ee seg80 | 1.27 → 0.92 | 86 → 49 | 4 → 0 | 15% → 0% | 79.1% → 7.4% |
| 000001ee seg81 | 1.18 → 0.88 | 113 → 133 | 4 → 2 | 29% → 0% | 67.3% → 18.4% |
| 000001f6 seg90 | 1.46 → 0.99 | 621 → 210 | 1 → 1 | 91% → 11% | 6.9% → 13.1% |
| 00000203 seg20 | 1.46 → 1.01 | 297 → 214 | 4 → 1 | 70% → 22% | 2.5% → 6.3% |

  EPS 한계 요청이 늘어난 두 구간은 기존 궤적에서 차가 목표보다 덜 돌던 순간(예: 목표 −2.67 vs 요레이트 −2.02 m/s²)이다. 이전에는 부풀려진 측정 때문에 덜 요구하던 것을 이제 실제 부족분만큼 요구하는 것으로 보이지만, 개방 루프라 확정할 수 없다. 실제 보낸 토크의 방향 전환 횟수(30 CAN 이상)는 47→46, 4→7, 11→7, 42→40, 31→19, 29→33으로 섞여 있다.
- 판다 GM 조향 검사(safety.h의 검사 함수를 파이썬으로 옮겨 같은 명령열에 적용): 300 초과 위반은 기존 기록 명령 125·27·0·130건 → 새 명령 0건. 운전자 토크 제한·변화율 위반 진입은 기존 4·5·8·1회 → 새 2·3·1·0회. 위반은 기존에도 있었다. carrot 판다는 감소 한계를 25로 선언하지만 호스트는 운전자 반대 토크 중에도 15씩(기존 8~13씩) 줄이고, 한 번 위반하면 검사기가 0으로 초기화돼 큰 커브 동안 연쇄 위반으로 남는다. 판다의 차단 줄이 주석 처리돼 있어 송신에는 영향이 없다. 판다는 이번에 건드리지 않았다.

## 검증하지 못한 것

- 실제 주행에서 증상이 사라졌는지. 개방 루프 재생에서 요청 부호 반전 횟수는 구간마다 늘기도 줄기도 했다(8→3, 4→7, 1→0, 4→5). 실차로만 판정할 수 있다.
- 판다 펌웨어 바이너리에서의 검사 결과(위 판다 수치는 소스 함수를 옮긴 계산), EPS의 물리 토크 한계.
- 재부팅 뒤 시동을 건 상태의 card·controlsd 실제 객체(오프로드에서는 이 프로세스가 뜨지 않는다. 같은 코드·설정으로 만든 별도 객체로 확인했다).
- FrogPilot 주행 당시의 실제 설정(기본값이면 NNFF 켜짐).

## 첫 주행 때

- 처음에는 완만한 커브에서 손을 핸들에 얹고 확인한다. 예전에 차선을 벗어났던 급커브를 첫 확인 장소로 쓰지 않는다.
- 이상하면 바로 개입하고, 주행 후 로그를 확인한다.
