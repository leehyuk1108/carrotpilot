# 트래버스 조향: 토크 한계 근처 튐·풀림 → FrogPilot과 로직 동일화 (2026-11-14)

## 증상 (사용자 제보)

- 11/11 수정 뒤 전보다 훨씬 나아졌다.
- 그래도 조향 토크가 실제 한계에 가까워지면 토크 그래프가 튀고, 조향을 풀었다 잡았다 한다.
- 같은 차에서 FrogPilot은 그러지 않았다. 파라미터는 빼고, 조향 로직이 다르면 FrogPilot과 똑같이 맞춰 달라고 했다.

## 로그로 본 것 (11/13 주행 10개 qlog 스캔 + rlog 6구간)

- 요청 토크가 0.9 이상인 구간에서 운전자 개입(steeringPressed)이 잡힌 프레임(364개)은 모두, 측정된 운전자 토크가 요청과 반대 방향이었다.
  - 원인은 확정하지 못했다. 큰 조향 토크로 핸들 축이 비틀린 측정, 운전자가 실제로 버틴 힘, 노면 반력이 모두 가능하다(가설).
- 요청이 0.6 이상인데 carOutput(호스트가 적용한 값)이 요청보다 깎인 프레임 중, 그 시점 운전자 토크로 계산한 허용치도 요청을 깎는 경우가 1,917프레임 중 1,198프레임(62.5%)이었다(운전자 토크 제한 `apply_driver_steer_torque_limits`, 반대 토크 약 1.4 Nm면 허용 0). 나머지는 변화 속도 제한(+10/−15)과 겹친다.
  - 메시지 시각을 맞추지 않은 계산이라 정확한 기여율은 아니다. carOutput은 EPS가 실제로 낸 토크가 아니다.
  - 관찰된 출력 감소('풀었다 잡았다')를 만들 수 있는 경로다. 활성 해제, 송신 시각, EPS 수용 등 다른 경로를 배제하지는 못했다.
  - 이 제한 함수와 상수(65/4/100, 상한 300, 3/10/15)는 FrogPilot과 글자까지 같다.
  - 코드가 같으므로, FrogPilot과의 차이를 찾는다면 제어기가 한계까지 얼마나 세게·자주 미느냐가 후보다(확정 아님).
- 21 km/h 급커브에서 요청이 1.0에 붙었다가 풀리며 0.8↔0.4로 출렁였다. 45 km/h에서 목표가 급변하자 요청이 0.3초 안에 −0.1에서 +0.9로 튀었다.

- 적용 범위: NNFF가 켜진 트래버스·트레일블레이저·트레일블레이저 CC·트랙스(`NNFF_FROGPILOT_PARITY_CARS`, 11/11 동등 처리 대상)만 해당한다. 다른 차는 그대로다.
- 정확히 말하면 'FrogPilot과 같은 계산식 + 사용자 설정 유지'다.
  - Kf: carrot은 앞먹임에 Kf를 곱한다. FrogPilot은 곱하지 않는다. Kf가 1이 아니면 적분 허용 판단에도 들어간다.
  - 지연: 첫 liveDelay 전에는 CP 지연을 쓴다. 0·음수·NaN이 오면 마지막 정상값을 유지한다. FrogPilot은 받은 값을 그대로 쓴다.
- 설정 스냅숏(11/14 03:3x 콤마에서 읽기만, 재생도 이 값 사용)
  - LateralTorqueCustom 1, Friction 0, KpV 140, KiV 30, Kf 120, Kd 0, AccelFactor 2000, NNFF 1, NNFFLite 0
  - LatSmoothSec 20, SteerActuatorDelay 30, CustomSteerMax/Up/Down 300/10/15, LatSuspendAngleDeg 300, UseLaneLineSpeed 200
  - 차량 기본 마찰(CP) 0.18은 제어기 시작 뒤 첫 9프레임(0.09초)만 쓰이고, 10프레임째부터 설정값 0으로 바뀐다. D02·D05의 현재 수치 효과가 없다는 말은 이 전제다.
- 그대로 둔 것(사용자 요청: 파라미터 제외)
  - Kp 1.4 / Ki 0.3 / Kf 1.2: FrogPilot NNFF 기본은 1.0 / 0.3 / 1.0. 한계로 미는 힘에 직접 영향이 있다.
  - 모델 쪽 `LatSmoothSec` 20(0.2초 + 불확실도 비례 추가 평활), `SteerActuatorDelay` 30(0.30초): FrogPilot은 평활 0, 학습 지연.
  - 차체 제원: carrot 무게 2090 kg, 무게중심 0.7, 타이어 강성 기본 1.0 / FrogPilot 1955 kg, 0.4, 0.444.
- 손대지 않은 carrot 고유 경로
  - 차선 기반 목표(UseLaneLineSpeed 200): 지금 설정에서는 쓰이지 않는다.
  - 횡 제어 일시 중지(LatSuspendAngleDeg 300°): 꺼진 것이 아니다. 운전자 개입 + 조향각 300° 초과가 약 1초 이어지면 조향을 끄고, 각도 15° 미만·개입 해제 때 돌아온다. 분석 구간(활성·5 m/s 이상)의 최대 조향각은 약 246°라 이 구간들의 원인은 아니다.
  - custom 조향 상한·변화량: 값(300/10/15)이 FrogPilot 기본과 같다.
- 별도 문제로 남긴 것
  - 판다 GM 조향 검사 실패가 송신 거부로 이어지지 않는 점(`//tx = false`)
  - 판다 rate 20/25
  - 학습 지연(lagd) 전처리 차이
  - 모델 출력 사용 방식(action head)

## 개방 루프 재생 (11/13 rlog, 콤마에서)

- 재생 기준선 확인(수정 전 6dd63078이 설치된 콤마, 재생 시점의 Params 사용)
  - 곡률 평활: controlsd는 자기 안의 지역 함수 `smooth_value`(controlsd.py 209행, DT_CTRL=0.01, 계수 0.095)를 쓴다. `drive_helpers.smooth_value`(DT_MDL, 계수 0.393)는 import하지 않는다.
    - 기록된 직전 desiredCurvature에서 한 단계를 예측하면, 0.095는 기록값을 97.0~98.7% 프레임에서 1e-3 m/s² 안으로 재현했다. 0.393은 20.3~25.7%였다(3구간, `steer_baseline.py`).
  - 목표 곡률: 재생에서 계산한 경로와 기록된 desiredCurvature 경로의 결과가 거의 같았다. 한계 비율 15.9/15.4/32.1/4.0/2.5/2.3%와 15.9/15.4/32.5/3.9/2.5/2.3%다.
  - 요청 토크: 설치된 제어기로 재생한 값과 기록된 토크의 차이는 중앙값 0.007~0.072였다(구간별). 적분 상태 차이가 한 원인으로 보이지만(재생은 한 구간 앞에서 적분 0으로 시작, 기록은 주행 전체의 적분) 항별 분해는 못 했다. 020e--10은 적분 차이 중앙값 0.051·토크 차이 0.049로 맞지만, 020f--4는 0.015·0.072로 다른 원인(송신·피드백 시각, 설정 차이 등)도 섞여 있다(가설).
  - 기준선 한계 비율 차이가 최대 3.4%p(020f--4: 기록 29.1%, 재생 32.5%)였다. 그래서 이 정도 이하의 차이는 효과로 보지 않는다(통계적 한계는 아님).

- 방법
  - 기록된 차 상태·모델 출력·학습 지연·자세를 그대로 넣어 요청 토크를 다시 계산했다.
  - 송신 토크는 같은 운전자 토크 제한과 변화 속도 제한으로 다시 만들었다.
  - 차 상태는 실제 주행 그대로라, 폐루프 결과 예측이 아니라 같은 상태에서 요청이 어떻게 달라지는지를 보는 비교다.
- 변경을 하나씩 켠 결과
  - 적분(D01)·지연(D03)·경사(D04)·상한(D16): 이 구간들에서 요청·포화·출렁임 차이가 재생 오차 안이었다. 효과가 없다는 뜻이 아니라 이 재생으로 크기를 가릴 수 없다는 뜻이다.
    - 상한: carrot 재생 이력에서 저크 제한 전 목표가 FrogPilot 범위(롤×g ± 3.0)를 넘은 비율(분모는 활성 프레임 전체)은 12구간 중 020d--5 5.8%, 020d--8 7.4%, 020c--9 1.0%, 나머지 0%였다. carrot 범위(4.5)는 모두 0%였다.
      - 실제 상한 작동률은 아니다. 실제 함수는 저크 제한을 먼저 적용하므로 이 값은 많게도 적게도 셀 수 있다. FrogPilot 상한이 걸릴 만한 구간이 있다는 뜻으로만 쓴다.
    - 상한이 목표를 자르면 요청 토크는 줄지만 경로를 덜 따라갈 수 있다. 한계 비율이 준 것을 개선의 증거로 보면 안 된다.
  - 평활 제거(D13): 요청 급변(10 ms에 0.1 넘게)이 2~5배, 출렁임 지표(초당 |Δ요청| 합)가 40~60% 늘었다.
    - 그래서 평활은 유지했다.
- 파라미터 가정(바꾸지 않고 재생만): Kp 1.4/Kf 1.2를 FrogPilot NNFF 기본 1.0/1.0으로 두면 다음과 같았다.
  - 요청이 한계(0.99 이상)에 붙은 시간: 32.9→10.1%, 15.5→10.3%, 15.1→12.8%, 2.3→0%. 앞의 둘(−22.8, −5.2%p)은 기준선 차이(최대 3.4%p)보다 크고, 뒤의 둘(−2.3%p)은 그 안이다.
  - 실제 주행 개선량이 아니라 같은 상태에서 요청이 얼마나 민감한지에 대한 값이다.

## 결론

- 남아 있던 로직 차이 6가지(D01·D02·D03·D04·D05·D16)는 FrogPilot과 같은 계산식으로 맞췄다(Kf 배율·잘못된 지연 방어는 위처럼 유지).
- 재생에서 본 것
  - Kp·Kf(파라미터)에 대한 민감도는 일부 구간에서 컸다. 실제 원인과 로직 변경 효과의 상대 크기는 확정하지 못했다.
  - 운전자 토크 제한(FrogPilot과 같은 코드)이 한계 근처에서 반대 방향 운전자 토크 때문에 허용치를 깎는 장면이 많았다. 반대 토크의 원인은 확정하지 못했다.
- 실차 효과는 다음 주행 로그로 확인해야 한다.
